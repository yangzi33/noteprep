# Curriculum scale check (RIS-60)

Question: does the Prepare picker still work if the catalogue grows to 10x or 20x today's size, and what is the smallest fix if not?

## Where the data lives and how it is loaded

| Step | Where | Notes |
|---|---|---|
| Source of truth | `data/curricula/<id>/<kind>-N/*.json` (committed) | Generated by `pnpm curricula:build` from `data/curricula-src`; hand-written for real/sample/synthetic kinds. Provenance fields (`sourceUrl`, ...) live here. |
| Validation | `validateDataset` per dataset, `validateCatalogue` across all | CI runs `pnpm curricula:build --check` and `pnpm curriculum:validate`. |
| Database | Postgres tables `curriculum*`, `topic_concept`, ... (read-only to the runtime roles) | Filled by the manual **Load curriculum dataset** workflow through the owner connection (`loadDataset`). Published versions are immutable. Provenance fields are not copied into the database; the JSON stays the record of them. |
| Picker | `createCurriculumDal` (`src/lib/server/dal/curriculum.ts`) | `/prepare` calls `listCurricula` once and `getSelectionPath`, `getSelectionSteps` and up to four `getSelectionOptions` per render. Each call reads the whole version tree (`loadTree`) of the selected version. Only the selected country's curricula are passed to the client component. |

## Method

`pnpm curriculum:scale-check` (`scripts/curriculum-scale-check.ts`). For each factor it builds a synthetic catalogue from the latest real suggested datasets, loads it into a throwaway database (own Postgres container, migrations applied), then times the data-layer calls the page makes (medians: 7 runs for the list, 5 for the picker sequence) and measures JSON payload bytes and table size. It measures the data layer, not a full Next.js render, so the numbers are a proxy for server time per request and exclude network and React.

Two growth shapes:

- **Breadth**: factor times as many curricula (copies of the real ones with new ids). By default the copies carry no concept links, so they are hidden, which is what new researched data will be until the generation engine supports it. `--keep-concepts` makes every copy selectable (worst case).
- **Depth**: one curriculum with factor times as many courses, units and topics as the largest real one (161 topics today).

Machine: developer laptop (WSL2), Postgres 17 (alpine) in Docker. Compare runs on the same machine only.

## Reading the numbers

- Breadth is cheap. The list query and the picker are dominated by the selected version, not by catalogue size, so 20x more curricula adds tens of milliseconds. Payload to the browser stays flat while copies are hidden and grows linearly with selectable curricula, to about 312 KB at 20x in the worst case. Because only the selected country's curricula reach the client, a real catalogue sits well below that.
- Depth is the one that grows with a single request: every picker call re-reads the whole version, and a render makes about six of them.
- Loading is a manual, offline step and scales linearly (about 0.4 ms per topic); 20x takes under 40 s.

## Fix made (small, no behaviour change)

`getSelectionOptions` rescanned the topic list for every unit, course and level when deciding what is hidden. It now builds three sets once per call (`supportedUnits`, `supportedCourses`, `levelsWithSupport`). Output is identical (the golden test below passes unchanged) and the depth x20 picker went from 122 ms to 91 ms.

## Verdict and size budget

No lazy loading or pagination is needed at 10x or 20x. `SIZE_BUDGET` in `src/lib/curriculum/validate-catalogue.ts` makes the limits explicit and CI-enforced (`pnpm curriculum:validate`):

- `topicsPerVersion: 4,000` (about 25x the largest real version, 161 topics, and just above the 3,220-topic depth x20 case, which ran at 91 ms).
- `topicsInCatalogue: 120,000` (counting the newest version of each curriculum; the measured x20 catalogue has 85,920 topics and a 87 MB database).

If a dataset ever needs more than the budget, the smallest next fix is not a bigger budget: either cache `loadTree` per request (about 6x fewer reads per page render) or have the unit and topic steps load only the selected course's subtree. Neither is implemented because nothing measured needs it.

## What the "no visible change" guarantee rests on

`tests/integration/hide-unusable.test.ts` walks every selectable curriculum, level, course, unit and topic through `listCurricula({ selectableOnly })` and `getSelectionOptions(..., { hideUnusable })`, hashes the result per curriculum and compares it to `tests/fixtures/curricula/selectable-golden.json`. A change that makes a hidden course visible, or hides a visible one, fails it. Regenerate only on purpose with `UPDATE_SELECTABLE_GOLDEN=1`. In addition, `pnpm curriculum:validate` prints the same dataset hashes as before this change for all existing datasets.
