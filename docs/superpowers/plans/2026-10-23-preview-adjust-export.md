# Preview -> Adjust -> Export: implementation plan (slices S1 to S6)

Status: approved direction (owner brief of 2026-10-23). Architecture reviewed by an Opus planning pass against `origin/main`. S4 and S5 need independent Opus reviews and real-database concurrency tests before merge. Decisions D-102 to D-108 in [decisions.md](../../decisions.md). Earlier design notes: [generation-flow](../../generation-flow.md).

Flow: Select -> free draft -> HTML preview -> adjust (Replace/Remove/Undo per question, Create Another Version) -> confirm export -> compile PDFs -> charge only on success -> download. Deterministic generator only (no LLM); every exportable question stays verified.

## Key decisions
1. **Drafts live in new tables**, not `lesson_revision`: `draft` (one per preparation: validated request, context snapshot stored once, `rev` for pointer CAS, `version_count`, `active_version_id`, status active/expired, `expires_at`) and `draft_version` (versions of one draft: `ordinal`, `seed`, `rev` for optimistic concurrency, `content` = verified `LessonPackage`, `content_hash`, `question_meta` {questionId: {level, origin}}, `next_question_seq`, bounded undo `history` of before-images, `changes` summary, `pending_candidate`). `app_runtime` cannot DELETE; `worker_runtime` purges. Rejected: reusing `lesson_revision.status='draft'` (burns revision numbers, forces a paid lesson shell, no concurrency column, purge would touch the historical-exports table).
2. **Item-source gate**: `src/lib/content/item-source.ts` with `ItemSource`, `RawItem`, `admitItem` -> `VerifiedItem`. Only verified items can enter a package; future LLM sources must provide structured math that passes the schema; no free LaTeX/HTML field exists.
3. **Question operations are pure functions** in `src/lib/package/draft-ops.ts` (reuse rehash and `validatePackage`): `questionSlots`, `drawReplacement`, `acceptReplacement` (new id `ex-{nextSeq}` at the same position and level), `removeQuestion` (min count), `undoLast` (restores before-image, asserts hash), `changeSummary`. The draft-side `question_meta` records each question's level (built by `buildPackageWithMeta`); the package schema and legacy hashes are untouched. Draft operations do not append to `pkg.adjustments[]`. Fix `adjust.ts` `add_exercises` id allocation (`startIndex = max id + 1`).
4. **Versions**: Create Another Version builds a new `draft_version` with a new seed (limit `MAX_VERSIONS_PER_DRAFT`, no auto-eviction, no confirm dialog because nothing is lost); switching only CAS-updates the draft pointer; every content mutation names `versionId` + `expectedRev`.
5. **Export (S4/S5)**: an immutable `export_snapshot`, an `export` entitlement row with a partial unique index `(owner_id, export_key) WHERE state IN ('pending','succeeded')`, a new job kind `export` (separate migration for the enum value), one `lesson` row per export (so existing download/ownership paths are reused), reservation made in the confirm transaction, consumption only in `commitExport` after stored objects are re-verified. Triggers: `generation_job_reservation_shape` extended to export; a deferred `export_state_consistency` trigger; export/snapshot guards. Details and invariants table below.
6. **Export identity**: `exportKey = sha256(exportContentHash + specHash)`; `exportContentHash` hashes a projection of what the renderer reads (not seed, adjustment log, provenance or inputs hashes); spec = sorted documents, locale, page format, template version, render version, validator version. Page format is lifted from the hard-coded `letterpaper` into a template parameter.
7. **Migration path**: `FLOW_MODE=legacy|draft` (default `legacy`) so `main` always works; S6 flips the default; legacy generate code is retired in a later cleanup.

- **S2 Question-level adjustment (L).** `draft-ops.ts`; DAL `requestCandidate`/`tryAnother`/`keepOriginal`/`acceptCandidate`/`removeQuestion`/`undo`; server-rendered per-question forms; candidate panel (original stays visible); changes indicator. - **S3 Versions, concurrency, limits (M).** `createVersion`, `switchVersion`, conflict banner, full limits wiring, sliding expiry. Tests R6, R7 (two parallel mutations on one rev: one succeeds, one conflicts), version limit, rate limits.
- **S4 Export reservation and idempotency (L, HIGH RISK).** Migrations `job_kind_export` then `export_tables`; `export-spec.ts`; DAL `confirmExport`/`getExportStatus`; `commitExport` and `settleExportFailure`; claim/list/sweep for export; confirmation page (full page, not a dialog); export status page. - **S5 PDF export and delivery (L, HIGH RISK).** Worker `runExport` from the frozen snapshot with the hash chain draft_version.content_hash -> snapshot -> render input hash -> manifest v3 -> stored objects; page format threaded through templates; deterministic compile flags; manifest v3 accepted by `getLessonView`. ## S4 invariants (mechanism -> test)
Per-account `profile FOR UPDATE` serialises spending decisions; idempotency replay plus live-key reuse prevents double click double charge; equivalent concurrent exports join one `export`; a `failed` export leaves the partial index so retry works; worker retry reuses the reservation; stale completion rejected by fencing token + job running + export pending + `WHERE state='reserved'`; success consumes once in a single transaction with a deferred consistency trigger; every terminal path calls `settleExportFailure`; the UI says "not used" only when the reservation row is `released`; the snapshot is copied in the confirm transaction and is immutable; confirm carries `expectedRev` and `expectedContentHash` so the user pays for exactly what they saw; historical exports are untouched (no DDL on revision/manifest, v2 manifests still accepted). READ COMMITTED with row locks suffices because spending decisions run under the profile lock, the bucket update is conditional, and live-export uniqueness is a unique index.

## Resource limits and TTL
All thresholds live in `src/lib/server/limits.ts` (zod from env, one `DEFAULT_LIMITS` object of owner-tunable placeholders): draft creation per user/IP/global, versions per draft, active drafts per user, candidates per user/slot, undo depth, min/max exercises, draft size, export concurrency and deadline, draft TTL (default 14 days, sliding), purge grace, purge batch, and future LLM token/cost keys. Enforcement reuses `rate_limit_window`. `ItemSource.draw` receives a `ResourceBudget` so LLM budgets plug in later.
